# Stored data after 2.0 migrates forward in frozen steps

Status: Accepted (2026-10-16, Canopi 2.1 target; built by the 2.1 foundation phases); amended 2026-10-17 (Q34 to Q36, Q40, Q47, Q45 pass; ledger 2.1-Q35r, 2.1-Q54, 2.1-Q67, 2.1-Q69, 2.1-Q82, 2.1-Q96, 2.1-Q112, 2.1-E4, 2.1-E6, 2.1-E7, 2.1-M9, 2.1-M15 to 2.1-M17); amended 2026-10-17 (the reader release: 2.1-Q137, 2.1-Q138, 2.1-M21, which withdraw E7 and M16, replace M15 and narrow M9 and M17; 2.1-M23 to 2.1-M25; the blocker review: 2.1-M31 to 2.1-M33; the readiness review: 2.1-M37, 2.1-M42); amended 2026-10-19 (stamp payload v3 and the Design additions: 2.1-Q155, 2.1-M88, 2.1-M94)

## Context

ADR 0021 refused data from before 2.0. In 2.0 every reader refuses any version but the current one, each store's version is a hand-written constant, so a bump without a step compiles, and Web keeps every Draft in one localStorage key that loses Drafts above a few MiB. The `.canopi` rules are 20 hand-written Rust and TS pairs with 13 drifts. The user decided that `.canopi` (2.1-Q6) and every local store (2.1-Q33) migrate forward in chained steps, the spec is generated and frozen (2.1-Q7), Web Drafts move to IndexedDB (2.1-Q8), and one Rust core serves both editions (2.1-Q34).

## Decision

- **One rule for all user work.** From 2.0 on, each release that changes a user-work store's shape ships one frozen vN-1 -> vN step for that store. Steps run in sequence when the store opens; a newer version is refused, unchanged, except where the reader release reads it (Rollback); data from before 2.0 is handled as ADR 0021 says.
- **User work or derived.** User work has a chain: `.canopi` (files, Drafts, stamp files), saved-stamp payloads, the settings record, the user DB tables, the library catalogue, source `meta.json` and the browser records. Derived stores (display COGs, previews, the image cache) have no steps: a bump wipes and rebuilds them.
- **A runner per store.** A store has a floor, its version at the v2.0.0 tag (`.canopi` 9, user DB 9, saved-stamp payload 2, settings 1, catalogue 25, `meta.json` 1, Web record containers 3; a 2.0 settings record has no version field and reads as 1), and an ordered list of steps; the current version is the floor plus the number of steps, so a bump without a step does not compile.
  - Outside `.canopi`'s additions rule below, a change that only adds (an optional field, a nullable column, a table) is still a frozen step that only adds, with its fixture; it never rewrites rows. A stored code id (tool, panel, command) unknown at read is dropped, never refused.
- **One store-open lifecycle:** opening, migrating, then ready, recovered, newer-read-only, refused-newer, set-aside-damaged or unavailable (`StoreOpenStatus` in `canopi-types`, one `SubsystemHealth` record from store id to status, read by one model in `failures/`). A migration writes a copy and swaps it in durably once verified. The plant catalog is a read-only row.
- **Degraded stores** (2.1-Q67). A store refused as newer or unavailable is never written for the session: settings run on defaults, user-DB features turn off, each with one notice that says changes are not kept; the library is read-only; the Design stays saveable. A store read as `newer-read-only` (the reader release, Rollback) is shown with its content and never written: settings apply their known fields, user-DB lists show read-only, with the same one notice per store.
- **Rollback by one release destroys no work** (2.1-E4, 2.1-Q138, 2.1-M21). Readers ship one release before writers: the reader release (the next 2.0.x after Phase 1, 2.1-M33) opens every 2.1 form (`.canopi` v10 files and Drafts, the IndexedDB Draft store, user DB 10, catalogue 26, settings record 2, the Web species-list record), and any later version of each, as `newer-read-only` and writes none of them. So 2.1 migrates each store in place, and a rollback by one release shows the latest work, read-only, with one notice per store.
  - A re-upgrade finds each store as 2.1 left it, so no replaced form is kept (2.1-E7 withdrawn). A store the reader release does not know (the Web Data library, Web stamps and the Notebook record) is left untouched by it.
  - The reader release reads a later version only through the fields, tables and literals it knows, and the rollback lane proves each later step readable; a step it cannot read ships its reader in a further stable reader release, proved by the lane on that release's candidate, before any published build writes it (2.1-M23, 2.1-M32, 2.1-M68).
  - A build from before the readers keeps to its own forms. On Desktop it refuses each 2.1 store unchanged, and 2.0 refuses a newer catalogue before any sweep, so no 2.1 library file is pruned; on Web it reads only its 2.0 keys, so every 2.1 record stays byte-identical. One bounded exception, on betas only: settings record 2 sits in user DB 9 from 2e until N2's user DB 10 step, so such a build reads the row and may rewrite it without the fields it does not know; those steps only add fields, so no 2.0 field is lost (2.1-M42).
  - Kept for reasons other than rollback: the `.canopi` pre-upgrade copy below; each migrated Desktop Draft's v9 form, kept once in `drafts/before-v10/` and never listed, because the v10 step reshapes the budget (2.1-Q96, Q162) and a Draft is the Design's only copy; on Web, the 2.0 Drafts key, unwritten until 2.2, and a new key for settings and each record whose shape 2.1 changes, because a tab older than the reader release may keep writing the v3 keys after a deploy (2.1-Q83).
- **`.canopi` admission** has four typed outcomes: current, before the floor, `Migratable{from}`, newer.
  - A migrated open is clean, so only a real edit writes. Before the first write in a new format on a Desktop file home, the old file is kept once beside it (`Garden (Canopi 2.0).canopi`) and a notice says so; an unwritable folder is named in the notice, which asks before saving (save state `copy-blocked`; 2.1-Q35r). A Web open makes a Draft and leaves the user's file untouched, and a migrated Draft is no user file, so neither shows the notice; a Desktop Draft's v9 form is kept by Rollback.
  - A failing step refuses with `migration_failed{from}`; the file is unchanged, and such a Draft is listed as unreadable. Migration runs once at the one decode choke point, on JSON values checked by the frozen vN-1 schema; every write passes the same admission as a read.
- **One core** (2.1-Q34). `canopi-format` (ADR 0023) owns the `.canopi` read checks, the chain, the writer and its admission, the wire conversion, the new-Design builder, typed refusals, the spec emitter, the Draft summary rule and the saved-stamp payload chain; Desktop runs it natively through executor-backed commands, Web as wasm in one worker. TS keeps the generated types, the adapter, the error mapping and the edit-time predicates.
  - The core also owns (Q45): an unnamed Design stores an empty name; Recent Designs refuse with Open's `DesignLoadFailureKind`; groups are normalised at decode and refused on write when dangling or under two members; unreadable Drafts are listed, never hidden.
- **The spec** (2.1-Q7) is emitted by the core into `canopi-format/spec/v<N>/` (schema, fields, new-Design defaults, a fixture cut from the tag covering every field with a non-default value and one unknown root key, and its hand-written expected output), frozen per release. IPC is not versioned.
  - The reader release freezes only v10's read schema, with a hand-made read fixture and its expected read output, because `DESIGN_FILE_FIELDS` still describes v9 then; Phase 2b emits the full `spec/v10/`, cuts v10's fixture from that first build that writes v10, and a release check holds the emitted schema equal to the frozen read schema or its `additions/` (2.1-M31).
- **Additions that keep the version** (2.1-Q36). From v10, an optional field valid alone, at the root or nested, and a new literal of an open set need no step; the release check accepts such a schema diff as `v<N>/additions/`.
- **The v9 -> v10 step** (2.1-Q69) is the only 2.1 `.canopi` bump: ramps, raster quantities and locales become open strings (a reader keeps an unknown literal and uses the documented default); every nested object gains an extension bag that keeps unknown keys; `plant_display` moves out of `extra` into a typed Document field.
  - The budget shows plants only, each line reduced to its target and unit cost, with one currency per Design (2.1-Q96), and keeps non-plant lines unshown in its extension bag (2.1-Q162). A 2.0.x from before the readers refuses a v10 file as newer; the reader release opens it read-only (Rollback).
- **Saved stamps** are relative arrangements in ground metres (ADR 0001, 2.1-Q78d; a 2.0 payload keeps its numbers, now read as ground metres), not `.canopi` objects. Each payload carries its version (floor 2; 2.1 adds one v3 step for guides, pinned names, locks, notes, species appearance and Q155's planning data, 2.1-M88); its chain is in `canopi-format`, run per row by each edition's stamp store (the user DB on Desktop, a browser record on Web, 2.1-Q112). `SavedObjectStampPayload` lives in `canopi-types`. An exported stamp file is a `.canopi`.
- **Settings** make their first shape change in 2.1 (the unit system, 2.1-Q120). Their chain is data in the settings field table: a step adds a field with its default, renames or drops a field, or maps a literal, and both editions' runners are generated from it, so no step is written by hand in two languages; a step that cannot be data moves the chain into `canopi-format` (2.1-E6). On Desktop the record stays the user DB's `settings` row (2.1-M17), migrated in place (2.1-M21).
  - Boot reads are synchronous on Web only; Desktop reads through a reserved UserData slot. A bad value resets only that field and keeps the rest, the Maps key included; the original record is kept once as `settings.before-reset` (a user-DB row on Desktop; secret, replaced by the next reset, never read by the app); one notice says what was reset, on both editions (2.1-Q54). Writes are patches of changed fields, so a write keeps keys it does not know and never overwrites a newer record.
- **Web Drafts** (2.1-Q8). One IndexedDB record per Draft with its `.canopi` version and a revision, compared and set inside one readwrite transaction; the store takes its `IDBFactory` (2.1-Q47). Persistence is requested on the first Draft with a one-line reason; if refused, the welcome screen and save status warn and offer Download .canopi (2.1-Q82; built in 2.0.3, 2.1-Q137). The first Web step copies every Draft, refused ones included, and verifies each canonical encode. A 2.0 tab writing after the move goes to that id's one "copied from an older tab" Draft, never overwriting the original.
- **An old tab meets a newer database** (2.1-Q40). It saves, closes its connection and shows the one "New version: Reload" notice that a deploy shows (2.1-Q83); the new tab shows `draft_store_blocked` while blocked; an older build refuses a newer store with `draft_store_newer`, shown as the same notice. A pending-write marker found at open names the Draft whose last change may be missing.

## Alternatives rejected

- **Refuse older files after 2.0.** Users lose their own work at each format change.
- **Two hand-mirrored codecs with a parity test.** Every step written and tested twice; the parsers already drifted.
- **One key per Draft in localStorage.** The quota stays shared and small.
- **Setting the whole settings record aside on one bad value** (ADR 0021). It loses the Maps key and every other choice.

## Consequences

- Supersedes [ADR 0003](0003-no-backward-compatibility.md) and [ADR 0013](0013-stored-data-migrations.md), and replaces the after-2.0 parts of [ADR 0021](0021-canopi-2-breaks-stored-data.md). Each format change names its step in the handoff; the scenario re-walk counts a format bump as one owner, the core.

## Checks

- A migration harness, `migration_steps_frozen`, the schema release check, `canopi_format_fixture_covers_every_field` and `no_design_field_holds_library_results` (to be created by Phase 2b); the oracle corpus (exists: `canopi-design-conformance.test.ts` and its Rust twin) run natively and through the real worker, plus round-trip property tests.
- Session scenarios and the Draft-store suite in Chromium, WebKit and Firefox (Phase 2b): the Q35r copy and `copy-blocked`, the Q40 cases, the 2.0 tab after the move, a 2.0 tab writing settings, favourites and recently viewed after the 2.1 deploy, the kept 2.0 key; a settings fixture with one bad field per type (Phase 2e); a model test that no write reaches a degraded store (Phase 1b).
- The rollback lane (Step 2.0.4): the readers, built from the release candidate on the frozen fixtures until the reader release is tagged and then from the latest stable 2.0.x tag (2.1-M37), run on each 2.1 store step's output, read it and write no byte.
  - On a maintenance-branch PR or candidate it builds them from that candidate and runs them on the fixtures and on what `main`, or the pending store step's branch, writes; the step merges once that reader is tagged (2.1-M68). From 2.1.0 on, the lane builds the readers from the previous stable minor's latest tag, and a step they cannot read ships its reader first from that minor's maintenance branch (2.1-M53).
- The D3 rollback test (Phase 4) installs the latest 2.0.x stable release (on Web, its rollback deploy with the kill-switch worker, ADR 0029) over 2.1.0's stores (`.canopi` v10, Desktop Drafts, the Web Drafts move, user DB 10, library 26 holding 2.1 imports and results, settings record 2, each moved Web record): each opens read-only with its latest content and no byte changes; a re-upgrade finds every store unchanged; the last 2.0.x before the readers (2.1-M33) then refuses each Desktop store unchanged and prunes no library file, and on Web leaves every 2.1 record byte-identical.
