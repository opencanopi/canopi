# Rust crates and native layering

Status: Accepted (2026-10-16, Canopi 2.1 target; built by the 2.1 foundation phases); amended 2026-10-17 (Q34 format core, Q37 engine procedure, Q47 fault seam, Q45 pass; the job-runner prototype and the module-map run: ledger 2.1-M4, 2.1-M5, 2.1-Q65, 2.1-Q79, 2.1-Q122); amended 2026-10-17 (the reader release: 2.1-Q138, 2.1-M21; the readiness review: 2.1-M44, 2.1-M46)

## Context

In 2.0 almost all native code is one Tauri crate. LiDAR is 57% of production code and depends on Tauri. Plant search calls user-DB favourites, so catalog depends on store; `design_files` names a desktop folder revealer, so store depends on desktop. Commands name an executor class 81 times and run LiDAR workflows themselves. The `.canopi` rules exist in Rust and in TS. The module-map run found 2 production SCCs, 14 LiDAR back-edge pairs and 29 sites of LiDAR extensions importing each other. The user chose the crates (2.1-Q9), an item-kind owner now (2.1-Q10) and one `.canopi` core (2.1-Q34).

## Decision

- **Thirteen crates, leaf first.**
  - `canopi-types` (renamed `common-types`): shared shapes and `DESIGN_FILE_FIELDS`, the failure catalogue (ADR 0025), the settings field table, the quantity table, the TS-facing command map (no `OpSpec`, which lives with each facade).
  - `canopi-format`: a leaf over `canopi-types` owning stored user work (ADR 0026): `.canopi` read checks, the frozen chain, the writer with admission, the wire conversion, the one new-Design builder, typed refusals, the spec emitter, the Draft content rules and the saved-stamp payload chain. It replaces `desktop/src/design/format.rs`; no tauri, tokio, sqlite or wasm-bindgen.
  - `canopi-search-text`: the one implementation of search normalisation (ADR 0027), with a key CLI for the catalog build. `canopi-format-wasm` (its read half in Step 2.0.4, the whole core in Phase 2b), `canopi-page-rules-wasm` (Phase 3 N4: search folding and the analysis parameter rules, 2.1-M104) and `canopi-library-wasm` (Phase 3 N5, 2.1-Q122, 2.1-M151: the library catalogue, leaves and engines for the Web library worker) are thin exports, each loaded by one adapter (ADR 0022).
  - `bindings-gen`: emits TS from `canopi-types`; never depends on Tauri. `canopi-redact`: a dependency-free leaf, the Rust redactor (`Redactor`, `RedactedText`; ADR 0025), linked by `canopi-support` and the `-wasm` crates.
  - `canopi-support`: the executor, durable files, hash, time, `acquire`, `move_aside`, the store chain runner (2.1-M157) and the one private `blocking::run`. Durable files sit behind a `DurableFs` seam with a fault implementation (kill after any step, disk full, read-only, rename failure, 2.1-Q47); `publish_durably(source, target, role, Precondition)` and `remove_durably` are the only way a Design, export, store, image-cache or library file is published or removed; a target lock (an owned `TargetLocks` value) makes the precondition check and the publish one step per target (2.1-M111).
  - `canopi-library` (renamed from the planned `canopi-lidar` at the crate split, 2.1-M4): the Data library, with no Tauri. `canopi-catalog` (only under 2.1-E1 outcome B): the plant DB and search. `canopi-store`: the user DB, settings record, favourites, recently viewed, saved stamps, Recent Designs, the notebook, Design files and Drafts. `canopi-desktop`: the Tauri shell, commands, host and composition. Crown detection adds `canopi-vegetation`, a pure-algorithm leaf called by `canopi-library`'s crown extension (L3).
- **Under 2.1-E1 outcome B, no edge between catalog and store.** Favourites and recently viewed are user data in `canopi-store`; `canopi-catalog` takes a set of names and returns projections; `canopi-desktop` composes the two. `design_files` returns the checked Recent Design file and the command reveals it, so `FolderRevealer` stays in `canopi-desktop`. Under outcome A the frontend composes the lists over the one catalog reader and this bullet is deleted.
- **Commands are one-line adapters.** Each service crate exposes async facade methods, such as `library.delete_item(id).await`, each declaring its lane, priority and deadline once as its `OpSpec` constant (ADR 0025). Command bodies make no executor call; a bounded synchronous flag signal is allowed. Rows live in `canopi-types`; one `commands!` table expands each entry into a private wrapper typed by its row, the handler list, and const checks that the entries equal the rows and each sync kind matches (2.1-M153).
  - A command adapts one facade method: a service-crate method with its `OpSpec`, or a method of the one composition facade `canopi-desktop::compose`, which only awaits service facade methods and the `FolderRevealer`, declares no `OpSpec` and makes no executor call (favourites, recently viewed, species search with favourite flags, Show in folder, the problem-report bundle). An operation spanning two lanes in one crate is one facade method awaiting two lane-scoped steps, each with its `OpSpec`.
- **Tokio is a per-crate rule.** `canopi-support` and the `native` feature of `canopi-library` take tokio `rt` (each facade is built at composition with its executor, which carries the `tokio::runtime::Handle`; no attach step and no optional executor slot; tests build their own); `canopi-desktop` keeps sync and time. There is no spawner trait; bare `tokio::spawn` and `tauri::async_runtime::spawn` are banned outside the executor and the runner's loop. Blocking work runs only through `blocking::run` (ADR 0025).
- **Infrastructure and composition homes.** `http.rs` (one client, `HttpPolicy`) and the tool runner (`process.rs`, the only `Command::new`; 2.1-M299) are in `canopi-support`; the native image cache in `canopi-catalog` (`canopi-desktop` under 2.1-E1 outcome A); `geocoder_fetch(url)` is a `canopi-desktop` command over support's HTTP and the shared host allowlist; Recent previews in `canopi-store`; the report's native sections and `app_folders` live in the `canopi-desktop` composition. The updater (`host/updater/`) is the one exception to the HTTP and process owners (2.1-M96).
- **Library internal order:** leaves (grid, `crs`, `kinds`, `lineage`, test hooks) < engines < repository < extensions < jobs < facade.
  - A `catalogue` feature builds the leaves, engines, repository, extensions' portable parts, jobs, janitor and facade for `wasm32-unknown-unknown` with `tokio::sync` only and SQLite through rusqlite 0.39 (2.1-M152); `native` adds the tokio runtime, `blocking::run`, the sidecar, `std::fs` and the lanes. `canopi-library-wasm` takes `catalogue`, so the Web library worker runs the same catalogue and engines (2.1-Q65, 2.1-M151); raster input arrives as a `Read + Seek` reader or bytes through `engines::raster_read` and `raster_write`, never a path, with no engine trait (2.1-M131).
  - `crs` is the one CRS authority (ADR 0014): transforms on `proj4rs` over the table's rows and reads wbgeotiff GeoKeys; no other module names a projection crate. It owns `grid_convergence(crs, lonlat)`, the clockwise angle from grid north to true north; no other module derives grid north.
  - `lineage` is one field per item: `Source`, `Analysis{provenance}` or `External{tool, date, notes, links}`, replacing `LibraryItemRole` and `provenance` in catalogue step v25 -> v26; out of date and Refresh exist only for `Analysis`. Every item has one `LibraryItemId` with a `library_items` identity row (kind, lineage tag, name key UNIQUE); the Design's Site data entry keeps only the id, and v10 drops its `kind` (2.1-M130).
  - Repository: the catalogue, all SQL, the one row decoder `decode(row)`, which calls `kinds::parse_kind`, store open and migrations. Its row structs carry domain types and refuse a corrupt row with a typed failure.
  - Extensions: one module plus a registry row per analysis and importer (ADR 0027), display preparation, sampling, generation and coverage. **No extension imports another**; a piece two need moves down to a leaf or an engine. Each module is assigned to one layer in `module_layering.rs`.
  - Jobs: the runner and the janitor (ADR 0024). The runner matches the job kind exhaustively and calls the extension's work function; no extension names the runner; the facade hands display preparation to the runner's display slot on the Job lane. `Runner::run(self)` is one future, driven by the executor natively and by `spawn_local` in the Web worker; recovery and writes take an `ExclusiveOwner` (single instance on Desktop, the `canopi-library` Web Lock on Web; 2.1-M151). Modules import by their defining path, not `lib.rs` re-exports.
- **The item kind has one owner now** (2.1-Q10): the closed enum `LibraryItemKind`, its `literal()` and `ALL` live in `canopi-types`, which `bindings-gen` emits from; the `kinds.rs` leaf owns `parse_kind`, the only parse of the stored literal; each layer owns its own exhaustive match on the kind, with no wildcard arm (2.1-M46, 2.1-M125).
  - The repository's `decode(row)` replaces the readers that assume a raster, and recovery calls the same function; each layer matches on the kind exhaustively, so the compiler lists what a new variant fills. Recovery refuses an unknown kind. The kinds are shaped for point clouds that are seen and profiled (display by class, height or intensity; a profile through them; 2.1-Q79), and the `Vector` variant comes in 2.1 with bring-your-own vectors (2.1-Q100); hydrology's vector outputs reuse it.
- **The whole-grid engine (L22)** is chosen at N0 among in-process crates that build for wasm32 and run single-threaded in the Web worker (2.1-Q37 narrowed by 2.1-M91, 2.1-M134); its consumers are hydrology, contours and sunlight. The GeoLibre CLI sidecar may stay only as a Desktop test oracle, never a product engine; the winner's one pin is `Cargo.lock`.
  - The same check decides the windowed terrain engine (slope, aspect, frost pockets), which must also run in the Web worker (2.1-Q65), so only in-process crates qualify; N1 moves Desktop's windowed slope onto it and adds aspect and frost pockets on it (2.1-M44), and N5 runs it as wasm.
- **Tests.** Behaviour tests run against the facade inside each service crate; no `test-hooks` feature exists. `canopi-desktop` keeps the generated command-map contract test, which checks that each command's facade declares an `OpSpec` and that a job facade returns a `JobId`.
- **A crate step's exit is structural.** Build times are information; a slowdown becomes a performance bead, not a reason to undo a crate.

## Alternatives rejected

- **Catalog and store inside `canopi-desktop`.** Keeps the edges that make both untestable alone.
- **The `.canopi` core as a cfg'd module of `canopi-desktop`.** tao, wry, tokio fs, ring and sqlite do not build for wasm32.
- **A one-method `TaskSpawner` trait.** One real implementation behind two wrappers.
- **Jobs below extensions.** The runner calls the work, so that edge pointed up the order (job-runner prototype).
- **A build-time threshold per crate step.** It lets speed reopen a structure the user decided.

## Consequences

- A mutant in a Tauri-free `canopi-library` rebuilds and tests only that crate (ADR 0028).
- `native_command_policy`, `module_layering`, `ci_lane_policy` and the coverage configuration change with each crate move; the `lidar-native` CI job and the AGENTS.md gate row take the new name.

## Checks

- cargo-deny (to be created by Phase 0; bans by Phase 3): Tauri only in `canopi-desktop`; tauri, tokio and sqlite never under `canopi-format`; wasm-bindgen only in the `-wasm` crates (one from Step 2.0.4, then N4's and N5's from Phase 3 in either order, 2.1-Q122); only `canopi-desktop` depends on both catalog and store; `sha2` only in `canopi-support` (wrappers). `cargo tree -p bindings-gen -i tauri` is empty.
- `cargo check --target wasm32-unknown-unknown -p canopi-library --no-default-features --features catalogue` in CI with a clang or zig C compiler (2.1-M152), and the contracts §8 and §9 suites under wasm-bindgen-test in Chromium, Firefox and WebKit (to be created by Phase 3 N1 and N5); ast-grep `native-only-in-native` (no `std::fs`, `tokio::runtime` or `blocking::` outside `native` modules).
- Rust SCC count 0 (`rust-scc` ratchet, Phase 0); `module_layering.rs` (exists), narrowed to the library order with the module-to-layer list and no extension-to-extension edge (Phase 3 N1).
- ast-grep (Phase 0, as ratchets): `tauri-only-in-shell`, `sql-only-in-repository`, `no-formatted-sql` (every crate), `canopi-decode-only-in-format`, `tracing-warn-only-in-failure-logger`, `http-client-only-in-http`; `crs-only-in-crs` (ratchet from Phase 0, 0 at Phase 3, then replacing the projection-crate test in `crs.rs`, which exists).
- clippy `disallowed-methods` (exists; Phase 3 N1 widens it): no `std::fs::rename` or `write` of a published path, no `SystemTime::now`, no `Command::new` outside the tool runner, no blocking call outside `blocking::run`.
- ast-grep `no-attach-step` (no `attach_*` setter and no `Option` executor field in a service crate, Phase 3 N1), `no-nested-lane-in-job-work` (Phase 3 N1) and `updater-plugin-only-in-updater` (Phase 0 F6); clippy `disallowed-methods` gains bare `tokio::spawn` and `tauri::async_runtime::spawn` outside the executor and the runner's loop.
- `native_command_policy::tests` (exists) gains "no executor call in a command body".
