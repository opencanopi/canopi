# System qualities

Status: Accepted (2026-10-17, Canopi 2.1 target; built by the 2.1 foundation phases; ledger [2.1-Q70 to 2.1-Q77, 2.1-Q123 to 2.1-Q126, 2.1-Q135, 2.1-E7, 2.1-M7, 2.1-M8, 2.1-M18](../decisions/2-1.md)); amended 2026-10-17 (release order: 2.1-Q137, 2.1-Q138, 2.1-M21, 2.1-M22, 2.1-M25; the blocker review: 2.1-Q136 read with 2.1-M18, 2.1-M29, 2.1-M34; the readiness review: 2.1-M39, 2.1-M45, 2.1-M47, 2.1-M48); amended 2026-10-19 (the ecosystem review: 2.1-Q141, 2.1-Q143, 2.1-M54, 2.1-M55, 2.1-M60, 2.1-M61, 2.1-M63, 2.1-M64)
Amended 2026-10-22 (the Phase 0 design check: 2.1-Q201, 2.1-Q203, 2.1-Q231 to 2.1-Q235, 2.1-M205 to 2.1-M207, 2.1-M210, 2.1-M213, 2.1-M214, 2.1-M216).

## Context

Canopi is designed for millions of users (2.1-Q70) with no backend ever (2.1-Q71), no collaboration (2.1-Q72) and diagnostics sent only by the user (2.1-Q74). Its first-class platforms are Linux and Windows (WebView2) Desktop, and Web on desktop browsers, phones and tablets (2.1-Q73); the macOS dmg is still published, unsigned as today, with no new macOS investment until the user decides (2.1-Q125, 2.1-Q135). The user has only Linux, so every other platform is checked on CI hosted runners and nothing assumes a hand check (2.1-Q77).

In 2.0 the only copy of a Web user's work can be evicted, a Web deploy strands open tabs, only Linux runs the real app in CI, and Web runs only in Chromium and WebKit.

## Decision
Each quality names its mechanism and its check. A check "planned" is created by the phase the plan names.

- **On-device data safety.** No byte of user work is lost or half-written by a crash, a full disk, a rollback or the browser.
  - Mechanism: `publish_durably` behind the `DurableFs` fault seam (ADR 0023), the Draft records' `IDBFactory` and the library worker's OPFS pool (2.1-M151); chained, frozen migrations on a verified copy (ADR 0026); the pre-upgrade `.canopi` copy (2.1-Q35r); rollback by one release destroys no work, because the reader release reads every 2.1 form and writes none (2.1-E4, 2.1-Q138, 2.1-M21; ADR 0026).
  - Web: persistence is requested on the first Draft with a one-line reason (existing unkept Drafts: the save-status warning's Keep my drafts, 2.1-Q198); if refused, the welcome screen and save status warn and offer Download a copy (2.1-Q82). A deploy keeps the previous release's files, so an open tab keeps working and shows one "New version: Reload" notice, saving before it reloads (2.1-Q83). Both ship in Step 2.0.3 on today's Draft store (2.1-Q137).
  - Check: the model-based Session, Draft, user-DB and LiDAR suites over the fault seams; the migration harness; the Draft-store suite; the rollback lane; a deploy-skew e2e (an old tab loads a lazy chunk after a new deploy).
- **Untrusted input.** Every file, Draft, catalog artifact, tile, geocoder reply and settings record is hostile until admitted.
  - Mechanism: a threat model per input in the native guide (source, size cap, parser, isolation; written by Phase 1 1a); size caps before parsing (`.canopi` 64 MiB on both editions, GeoJSON through one bounded reader, rasters by the cell cap); readers return typed refusals and never panic (clippy `unwrap_used`, `expect_used` and `panic` denied in reader modules).
  - Decoders of untrusted input run in workers (the `.canopi` decoder in the format worker on both editions, 2.1-M154), and the page-rules wasm, pure rules over typed values (text folding, analysis parameter rules), in the page (2.1-M48, 2.1-M104); the CSP is generated from the one origin table, `policy/origins.json` (origin, purpose owner, directives, editions, phase), which emits both the Web `_headers` CSP and the `tauri.conf.json` CSP, held by a drift test, report-only for its first deploy, then enforcing, with `'wasm-unsafe-eval'` for wasm (2.1-M3, 2.1-M61).
  - Check: cargo-fuzz on `canopi-format` admission and chain, the GeoJSON reader and the LiDAR and raster readers (scheduled lane; each crash a corpus case and a test); a CSP test that every origin the code contacts is in the table.
- **Platform matrix.** Every platform runs the real app in CI; a platform lane that cannot run fails, it is never skipped silently, and the CI lanes themselves are the check.
  - Desktop: Linux WebKitGTK and Windows WebView2 run the Desktop real-app suite (2.1-M2, 2.1-M7), a WebdriverIO suite in `e2e/platform/` over tauri-driver with no in-app plugin, command mocking off (2.1-M60, 2.1-M213); Playwright cannot drive a WebDriver session, so the shared Playwright suite stays the browser suite. It covers the paths only the real shell has: file home save and Save as, the close guard and Quit, single instance, the asset protocol, the native catalog, the library and a job. Native file dialogs are answered by a debug-feature dialog seam in the desktop host.
  - macOS Desktop keeps today's CI build, native tests and dmg package (2.1-Q135), but is not tested by the Desktop real-app suite or a smoke, and no 2.1 work designs for WKWebView, until the user decides (2.1-Q125). Safari users are covered by WebKit in the browser suite.
  - Web: Chromium, WebKit and Firefox (2.1-Q84) run the browser suite; phone and tablet layouts run as a smoke in the iOS simulator on a macOS runner and an Android emulator on a Linux runner. The iOS simulator smoke and F6's macOS update probe, with its release check if clean (2.1-Q136), are the only macOS-runner test jobs 2.1 adds; the smoke checks Web on phones, not macOS Desktop (2.1-M18).
- **Release safety.** A user installs only what Canopi's release built, and the app installs only an update Canopi signed.
  - Distribution: Windows NSIS exe and MSI; Linux AppImage and `.deb` downloads with published checksums, no apt repository (2.1-Q126; Flatpak is a possible later channel, not planned); the macOS dmg published unsigned as today, with no Developer ID or notarization, not tested by the Desktop real-app suite (2.1-Q135); it self-updates only if the unsigned update probe is clean (2.1-Q136). The Q136 probe is clean only if it also passes `update install during an unsaved edit keeps the edit` and the unsaveable-settings close test (2.1-M97).
  - Windows signing (2.1-Q124): SignPath Foundation is the target. Until it is granted, releases keep today's unsigned exe and MSI for current users, with the SmartScreen warning as the named residual risk; from the grant, one stable publisher identity signs every Windows artifact, through `bundle.windows.signCommand` after the CLI's binary patching so the per-installer updater keys stay (2.1-M55).
  - Self-update (2.1-Q123, 2.1-Q138): the Tauri updater, landed with the release smoke in Phase 0 F6, before the first beta; two channels, stable and beta, and each finished 2.1 phase publishes a Desktop beta, while 2.1.0 closes the foundations (2.1-M22); Web has no betas in 2.1 and reaches users at each stable release (2.1-Q201). Its artifacts are signed with the updater key (a CI secret; the public half ships in the app), each channel is one static endpoint published with the release, and the app refuses an update whose signature fails.
  - The app checks for updates once per launch, quietly and silent offline, when "Check for updates at launch" is on (default on; the user-DB key row `updater.check_at_launch` until 2e, 2.1-M206), and from About's "Check for updates"; an available update shows one non-modal notice that opens About, and the download starts only from About (2.1-Q164, 2.1-Q235). `host/updater/` alone names the plugin; `check` and `download` run inside the executor's Network lane, one at a time, the payload capped; its states and codes are contracts §2 and §3 (2.1-M96, 2.1-M207, 2.1-M210).
  - Updater hardening: the app also refuses an update whose signed version is not newer (`requireSignedVersion`, no downgrades; the Windows installers keep `allowDowngrades`, so a rollback installs by hand, 2.1-M64); the updater runs in the Rust host, and the webview holds no `updater:*` permission (2.1-M54). Windows installs only after the one close request (ADR 0024; until then the close guard's flush, 2.1-M55, 2.1-M63), since its installer quits Canopi; a pending-update marker makes the next launch show "Update not installed" when the version did not change (2.1-Q234).
  - Channels: joining beta is installing a beta build, leaving is reinstalling stable; betas go to the user and invited testers, never offered in the app (2.1-Q139, 2.1-Q140); channel files live on a Canopi-owned host, each uploaded after its artifacts (2.1-M27), as GitHub release assets (stable.json on the latest release, beta.json on one fixed pre-release tag CI moves) that `updates.projectcanopi.com` redirects to (2.1-Q231, 2.1-Q250); the channel is the version's pre-release label and the endpoints one data file (2.1-M205).
  - Linux self-update (2.1-Q143): the AppImage and the `.deb` both self-update; for the `.deb` Canopi verifies the payload and runs `pkexec dpkg -i` itself, and with no pkexec About offers the download link (2.1-Q232). Linux installs while Canopi runs, then saves and restarts; a dismissed prompt, a `dpkg` error or an AppImage replace error (backup restored) keeps the Design open with "Update not installed" and the reason (2.1-Q233).
  - Check: the release smoke installs and launches each artifact on Linux and Windows; an update artifact without a valid updater signature or channel entry fails the release, and so does an unsigned Windows artifact once the grant exists; an updater e2e moves an installed N-1 to N (AppImage, `.deb`, Windows) through a local static endpoint and refuses an old signed artifact announced as newer.
- **Accessibility.** axe-core (a per-surface, per-rule ratchet that only shrinks, 2.1-M214), ARIA snapshots of each surface and keyboard-only flows for every user path block CI on Linux (Chromium, WebKit and Firefox, 2.1-Q84). Screen-reader runs (NVDA on Windows; VoiceOver waits for a macOS decision, 2.1-Q135) are a non-blocking smoke whose findings become beads.
- **Performance budgets.** Measured, not optimised: bundle size per chunk, cold start to an interactive start screen, opening the large fixture Design, and a fixed scripted pan and zoom of the large fixture Design in Chromium on Linux, measured as the median of five runs of long tasks over 50 ms and frames over 50 ms; raw frame time is recorded as information, not gated, because hosted runners draw WebGL in software on shared cores.
  - Each budget is a ratchet entry with a tolerance, baselined by Phase 0 F3c on `main` after the Phase 0 toolchain upgrade (2.1-M39, 2.1-Q141). Bundle size per chunk blocks: a rise past it fails and becomes a bead, never a raised budget without the user's dated decision. The timings are recorded as information until a 5-run CI spread probe shows a spread within tolerance, then block the same way (2.1-Q203).
- **Static Web serving.** No server logic (Step 2.0.3, 2.1-Q137): every asset, catalog and font file has an immutable, content-versioned URL; a small manifest names them and is `no-cache` (with `sw.js` from W1), and `index.html` (the entry and SPA fallback) revalidates by Pages' default (2.1-M178); `.parquet` ranges are answered by a zone Cache Rule (2.1-Q183); no file exceeds 25 MiB (the Pages cap of 26,214,400 bytes). The catalog manifest is itself an immutable content-named file whose name the page bundle carries; a page never looks it up through the edition manifest (2.1-M101).
  - The DuckDB-WASM binaries are larger than the cap (35 to 41 MB in 1.33), so they are served from a Canopi-owned R2 bucket on a `projectcanopi.com` subdomain under immutable versioned keys, never a third-party CDN (2.1-M8). They are named in the manifest and the CSP origin table and served with CORS, so the service worker can cache them. The Pages artifact still refuses a raw DuckDB wasm.
  - Previous release kept (2.1-Q83): each upload is this release's files plus every file named by the previous release's manifest, taken from the previous release artifact and verified by its checksums; files only N-2 named are dropped. On a path both name, this release's file wins; only `index.html`, the manifest, `sw.js` (from W1) and deploy-owned files may differ (2.1-M25, 2.1-M34). The 20,000-file and 25 MiB checks run on the merged set.
  - Service worker (2.1-Q116): it caches the app shell and the DuckDB binaries, and caches each catalog piece as it is read: fixed-size blocks of an immutable catalog file, each stored as a whole entry keyed by file and offset, because the Cache API stores no 206 and matches no Range; "Keep the catalog for offline use" fetches every block (2.1-M100). It answers HEAD and Range requests itself, assembling a 206 with Content-Range and Accept-Ranges from cached blocks and fetching only missing ones. Web opens and edits Drafts offline.
  - "Keep the catalog for offline use" is a choice the worker owns in IndexedDB `canopi-sw` (store `prefs`, key `keep_catalog`), which the page reaches only by `postMessage`. A tab calls `registration.update()` on focus, on becoming visible and after a failed lazy import; that call, not the browser's own checks, is how a tab learns of a deploy or a rollback (2.1-M99).
  - DuckDB runs in a same-origin worker URL, not a blob wrapper, so its requests pass through the service worker. The app caches are named per release, and the previous release's is kept while a client uses it; catalog blocks live in one cache per immutable catalog file, kept while a release in use names that file, and a new worker's install fetches the kept catalog's newly named file before it activates (2.1-M45).
  - Reload saves first, then marks this tab as reloading and sends `skipWaiting`; only a tab so marked reloads on `controllerchange`. In any other tab of the old release a controller change raises the one notice, never a reload, and that tab saves before its own reload (2.1-Q83, 2.1-M99).
  - A Web rollback deploy publishes a kill-switch `sw.js` that calls `skipWaiting()` at install, never `claim`, posts the rollback message to its clients at activate and unregisters, so it keeps serving the old tabs from the per-release caches and sends new navigations to the network (2.1-M25, 2.1-M29, 2.1-M36, 2.1-M99). Each open tab shows the one "New version: Reload" notice, saving first and offering Download a copy if that fails (2.1-Q83). The rollback target deletes the 2.1 caches and the `canopi-sw` record at start once no worker controls it and no tab answers on a BroadcastChannel.
  - W1 first proves two risks: a probe that the R2 host serves the wasm with Range and the CORS headers the worker needs, and a prototype of DuckDB offline through the service worker in Chromium, WebKit and Firefox (synchronous XHR from a worker under a service worker is unproven in WebKit). `web_release.py package` builds the release archive and owns its name, which keeps `-root-`; one notices file, from cargo-about and rollup-plugin-license, ships with Web as with Desktop (2.1-M216).
  - Check: `web_release.py`, the one owner of the deployment limits, refuses a mutable asset name among this release's files, and on the merged set a file over 25 MiB, a raw DuckDB wasm, a missing manifest entry or a differing collision; the deploy-skew e2e deploys N-1 and then N to a Pages preview project and drives an N-1 tab through a lazy chunk and a catalog read, and the N-1 tab's catalog read admits N-1's catalog manifest; an offline e2e opens a Draft and searches the kept catalog; a CI probe against the deployed site and the R2 host checks the range, CORS and cache headers.

## Alternatives rejected

- **A hand check per platform before release.** The user has only Linux.
- **A signed apt repository.** The user chose downloads only (2.1-Q126).
- **A macOS smoke, Developer ID or notarization now.** The user keeps the dmg as today for existing users and defers new macOS work (2.1-Q125, 2.1-Q135).
- **Screen readers as a blocking gate.** Automation is real only for VoiceOver and NVDA, and it is not yet stable enough to gate.

## Checks

- The lanes and checks named above (planned: Step 2.0.3, Phase 0 F3, F5 and F6, Phase 1 1a, Step 2.0.4, Phase 2b, Phase 3 N1 and W1, Phase 4 D3).
- W1 and D3 e2e: `Q83: manifest, waiting worker, kill-switch and store-newer each raise one Reload notice through the lifecycle port`; a tab that never navigates gets a deploy and then a rollback after a focus event; `Q83: Reload in one tab of release N reloads only that tab; a second N tab with unsaved edits keeps them, shows the notice and saves before its own reload`; a 2.1 tab is not reloaded when the kill-switch activates and no 2.1 cache is left after the next visit; Keep the catalog survives a deploy with a new catalog file (offline search).
